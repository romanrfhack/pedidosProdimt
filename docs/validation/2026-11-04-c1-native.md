## Secuencia obligatoria

1. **WSL: fuente y navegador.** `PRODIMT_Desplegar_C1_WSL.sh` comprueba hashes,
   recupera el commit exacto del bundle y ejecuta
   `tests/e2e/run-c1-browser-gate.sh --source SHA_COMPLETO`. Requiere Node 24,
   checkout limpio, ambos lockfiles, build, componentes, tipado y los **240
   casos de navegador correctos, sin omisiones ni flakiness**. Chromium se
   descarga para el usuario, sin elevación ni cambios globales; también se
   admite un ejecutable configurado explícitamente. No hay opción para saltar
   este control al aplicar.
2. **VPS: comprobación de base.** El instalador comprueba identidad exacta de
   I23, historial, configuración, salud y materiales del candidato. `--apply`
   exige el JSON de navegador del mismo commit antes de preparar o detener
   la aplicación. La API de esas pruebas es **simulada**: no acredita SQL ni
   aceptación de negocio.
3. **SQL aislado: siete casos EF/HTTP y SQL exacto.** Ejecuta las pruebas
   portátiles con los binarios C1 y el ensayo 18→19 en bases UUID temporales.
   Debe verificar rollback, replay, permisos de aplicación, preservación y
   limpieza. Las credenciales SQL se solicitan ocultas y no se incorporan al
   paquete. Un fallo detiene la entrega antes de detener PRODIMT.
4. **Respaldo antes de DDL operativo.** Conserva snapshot privado de
   configuración/release y verifica el respaldo SQL `COPY_ONLY`, `CHECKSUM`
   y `RESTORE VERIFYONLY`. No hay inicialización de otra base operativa,
   rotación de claves, revocación de tokens ni cambio de contraseñas.
5. **Migración y activación.** Con la API detenida, aplica la ampliación
   aditiva, verifica la conservación de las 33 tablas del contrato y el
   historial esperado; persiste el checkpoint de migración/preservación
   antes de activar los releases C1 y reiniciar la API.
6. **Cierre.** Verifica backend, frontend, salud y estado de recuperación.
   Sólo el reporte del destino `updated/completed`, 19 migraciones y
   `recovery_pending=false` permitirá registrar C1 como instalado. Una
   repetición ya saludable devuelve `already_current` sin repetir DDL.

El instalador se ensaya con fallos en los límites de recuperación. El marcador
de recuperación se escribe de forma atómica y con sincronización a disco;
conserva el checkpoint `migrationVerified`. Si C1 pudo aceptar escrituras o
ya se cruzó el límite de DDL, se recupera **hacia delante con el mismo
paquete**. No hay restauración automática de base, downgrade de binarios
históricos ni reducción de la columna que pueda borrar evidencia. El `Down`
de la migración rechaza contenido que ya no cabe en la columna antigua.
