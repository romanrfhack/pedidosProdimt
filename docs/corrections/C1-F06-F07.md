# C1 — F06 y F07: evidencia completa y límites de notas

Fecha: 3 de noviembre de 2026 (Ciudad de México). Base: I23 instalado `aa802e2`, corrector SQL y evidencia posterior integrados en `cbc34aa`.

## F06 — Auditoría del perfil excede la columna SQL

**Estado:** corrección implementada; aceptación SQL y despliegue pendientes.

El perfil puede registrar más de 2000 caracteres al conservar los IDs, abreviaturas y reglas de máquina por producto. La auditoría de seguridad comparte `AuditLogs.MetadataJson` y puede exceder ese límite al registrar asignaciones de permisos. No existe un snapshot histórico alternativo que permita reemplazar esos detalles por un enlace o hash sin perder evidencia.

Se elimina exclusivamente el límite EF de esa columna y se añade la migración **`20261104041928_ExpandAuditMetadata`**, que amplía `nvarchar(2000)` a `nvarchar(max)`. Se conservan el JSON completo, IDs de eventos, autor, versión, transacciones y contratos. Los límites vigentes de los comandos y abreviaturas permanecen; no se introduce un máximo artificial de productos ni se fragmentan eventos.

`Down` rechaza la reducción si cualquier valor ocupa más de 4000 bytes UTF-16; no trunca historia. Una reversión de la aplicación puede conservar la columna ampliada. No se modifican las migraciones ya instaladas ni las guardas/pines de I23. El diseñador y snapshot se generaron con EF Core 10.0.8.

**Regresiones:** perfiles sintéticos de 9 y 20 productos conservan todos los IDs, abreviaturas, herencia y versión en SQLite, y comprueban que el modelo no declare el máximo antiguo. `AuditMetadataSqlTests` agrega los mismos casos mediante HTTP/SQL, verifica rollback de perfil/versión/auditoría ante un error deliberado en el actor y prueba Unicode extenso sin truncamiento. Otra prueba usa una base UUID independiente para verificar la ampliación con filas previas y rechazar el downgrade ante JSON con espacios finales que supera 2000 caracteres (DATALENGTH, no LEN). Estos últimos requieren SQL Server real y no se declaran ejecutados aquí.

**Entrega:** requiere un nuevo paquete nativo compatible con 18→19 migraciones, respaldo verificado y ensayo de SQL exacto, rollback/replay y permisos en base temporal antes de operar producción. No ejecutar el instalador antiguo de I23 sobre esta fuente.

## F07 — Notas de revisión sin validación coherente

**Estado:** corrección implementada; pruebas locales realizadas; despliegue y aceptación visual pendientes.

El esquema permite **DeliveryNotes: 500**, **InternalNotes: 1000** y **Line.Notes: 500** caracteres UTF-16. `OrderNoteLimits` centraliza estos valores para validación y mapping EF. Captura administrativa directa/abreviada, NoOrder administrativo, captura cliente y revisión comparten la misma regla; corrección y creación de partidas usan el mismo máximo de línea.

La revisión valida ambas notas antes de cargar o mutar el pedido, cualquiera que sea la decisión. Las entradas que exceden el máximo producen `ArgumentException` con nombre del campo y el límite; el adaptador HTTP existente responde 400. No se recorta ni normaliza silenciosamente el texto. Un rechazo no modifica cantidades, fecha/hora, estado, versión, auditoría ni avisos. La vista de revisión añade `maxlength` 500/1000 y mantiene el borrador cuando el servidor rechaza el envío (coordinado con F04).

Al corregir F07 se identificó que el resumen de una revisión con muchas partidas también podía exceder sus 500 caracteres. Para esos casos el resumen expresa el número de campos cambiados; los valores completos anteriores/nuevos siguen en `MetadataJson` sin recorte. Una regresión con 20 partidas, notas de línea de 500 e internas de 1000 comprueba ambos eventos y su evidencia completa.

**Regresiones:** límite exacto y límite+1 en notas de entrega/internas/línea; decisiones aceptar/rechazar; captura directa/NoOrder sin escritura parcial. Pruebas HTTP con datos ficticios y reloj de negocio fijo verifican 200/400, error de campo y conservación del detalle e historial. Los tests HTTP usan almacenamiento en memoria; no sustituyen SQL Server.
